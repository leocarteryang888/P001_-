# 组合式空调机组选型软件——现有界面改造需求说明（Codex 执行稿）

> 用途：基于现有选型软件继续修改，不建议推倒重做。本文根据现有项目管理、机组创建、机组截面、功能段编排界面截图整理，作为 Codex 阅读现有代码、定位窗体/控件/数据模型并实施改造的需求基线。

## 1. 改造目标

现有软件已经具备较完整的工程管理、机组创建、截面选择、功能段组合、DWG 出图等框架。此次改造的核心不是重写 UI，而是在现有软件基础上建立一套更规范、可持续扩展的组合式空调机组选型流程：

1. 保留现有工程管理和机组组合操作习惯；
2. 优化机组创建流程，把项目级参数、机组级参数、设计工况、限制条件分层；
3. 统一各功能段的“输入参数 → 自动计算结果 → 图面 → 输出参数”结构；
4. 第一阶段重点保证机组图面、尺寸、功能段参数及 DWG/报告输出；
5. 暂未实现自动选型的功能段允许手动输入，后续逐块接入计算模块；
6. 所有参数从第一版开始建立统一字段 ID、单位、来源和数据映射，避免以后自动选型时重构数据结构。

## 3. 新版总体业务流程

```mermaid
flowchart TD
    A[新建/打开工程] --> B[录入工程信息和地区气象参数]
    B --> C[新建机组]
    C --> D[选择机组模板/空白机组]
    D --> E[录入机组设计条件与限制条件]
    E --> F[选择机组截面 W×H]
    F --> G[建立功能段序列]
    G --> H[逐段录入输入参数]
    H --> I{该功能段是否已有自动选型算法}
    I -- 是 --> J[执行自动计算/设备选型]
    I -- 否 --> K[手动填写设计结果]
    J --> L[形成统一输出参数]
    K --> L
    L --> M[自动生成/更新功能段图面]
    M --> N[尺寸与接口校核]
    N --> O[机组总成预览]
    O --> P[生成报告/参数表/DWG]
```

## 4. 机组创建界面改造

建议把现有“模板选择 → 截面 → 功能段”的分散输入，整理为向导式流程，但仍允许用户随时返回修改。

### Step 1：机组基本信息

字段建议：
- 机组方案号
- 客户编号
- 机组名称/位号
- 机组数量
- 机组类型
- 使用季节：夏季 / 冬季 / 冬夏季
- 安装位置：室内 / 室外
- 气流方向：左进右出 / 右进左出 / 自定义
- 接管方向：左式 / 右式 / 自定义
- 电源：默认 AC380V/3Ph/50Hz，可修改

### Step 2：核心设计输入

必须允许录入：
- 送风量 m³/h
- 新风量 m³/h
- 新风比 %（与新风量联动，二选一主输入）
- 回风量 m³/h
- 排风量 m³/h
- 机外余压 Pa
- 夏季室外干球/湿球或 RH
- 夏季室内干球/湿球或 RH
- 冬季室外干球/湿球或 RH
- 冬季室内干球/湿球或 RH
- 冷水供/回水温度 ℃
- 热水供/回水温度 ℃
- 冷媒类型及蒸发/冷凝工况（直膨机组启用）

### Step 3：限制条件

新增独立“限制条件”区域：
- 最大机组宽度 mm
- 最大机组高度 mm
- 最大机组总长度 mm
- 最大单段长度 mm
- 检修空间限制
- 运输分段最大尺寸
- 运输分段最大重量（预留）
- 电源限制
- 噪声限制 dB(A)
- 风速限制 m/s
- 客户指定品牌/材料/特殊要求

**原则：**限制条件不一定参与第一阶段自动计算，但必须保存到机组对象，并在后续选型/校核时可调用。

### Step 4：截面选择

继续使用现有 W×H 矩阵，但增加：
- 推荐截面突出显示；
- 当前选中截面的宽、高、面积、风速实时显示；
- 超过最大宽/高限制的截面自动禁用或警示；
- 支持手动输入非标准截面；
- 确认后写入机组主数据，不要仅保存在 UI 控件状态中。

### Step 5：模板/段序

用户可以：
- 从公共模板创建；
- 从个人模板创建；
- 创建空白机组；
- 从已有机组复制；
- 创建后自由修改段序。

## 5. 功能段统一数据模型【核心】

所有功能段必须遵循同一接口思想：

```text
FunctionSection
├─ identity      功能段身份
├─ geometry      尺寸/位置
├─ input         用户输入
├─ calculation   自动计算中间值
├─ output        对外输出结果
├─ interfaces    水/电/冷媒/排水等接口
├─ drawing       图面资源与绘图参数
├─ validation    校核结果
└─ metadata      数据来源/版本/人工修改标识
```

建议基础字段：

```yaml
section_id: UUID
section_type: cooling_coil
section_name: 冷水盘管段
sequence: 4
length_mm: 700
width_mm: 3200
height_mm: 1770
input: {}
calculation: {}
output: {}
interfaces: []
drawing:
  symbol_id: coil_chilled_water_v1
  view: side
  scale_mode: fit
validation:
  status: pass
  messages: []
metadata:
  calculation_mode: manual|auto|mixed
  manually_overridden: false
```

### 统一规则

1. **输入参数**：用户/工程条件给定，原则上不由本段随意改写；
2. **计算参数**：程序内部中间量；
3. **输出参数**：报告、图纸、下游功能段真正调用的数据；
4. **人工覆盖**：任何自动计算结果允许有权限的用户修改，但必须记录 `manually_overridden=true`；
5. **单位统一**：数据库存储采用统一工程单位，UI 可以转换显示；
6. **字段 ID 不使用中文标题作为唯一键**，中文仅作为显示名称。

## 7. 功能段图面改造要求

当前软件已经能绘制简化的混合段、过滤器、盘管、风机等图形，应保留现有绘图能力并逐步升级。

### 图面原则

1. 图形与计算数据分离；
2. 每个功能段拥有标准绘图组件；
3. 绘图组件根据 `width/height/length/设备数量/方向` 自动缩放；
4. 不能把整台机组做成一张静态图片；
5. 每段独立生成，再按 sequence 拼装；
6. 前移、后移、插入、删除功能段后自动重排坐标和尺寸链；
7. 图面应支持侧视图为第一优先，后续再扩展俯视/正视/3D；
8. DWG 输出必须使用同一套几何数据，避免屏幕图与 DWG 两套尺寸逻辑。

### 第一阶段需要规范的图块

- 新风/回风/混合段
- 检修/中间段
- 初效过滤
- 中效过滤
- 高效/HEPA过滤
- 活性炭过滤
- 静电除尘
- 冷水盘管
- 热水盘管
- 直膨盘管
- 电加热
- 蒸汽加热（预留）
- 送风机/回风机
- 消声器
- 蒸汽加湿
- 电极/电热加湿
- 湿膜加湿
- 喷淋段
- 板式热回收
- 转轮热回收
- 热管热回收

## 9. 输入与输出的传递关系

必须建立统一上下游数据链。

示例：

```mermaid
flowchart LR
    A[工程气象参数] --> B[机组设计工况]
    B --> C[混合段]
    C -->|混合空气状态| D[过滤段]
    D -->|空气状态+阻力| E[冷却盘管]
    E -->|出风状态+阻力| F[加热段]
    F --> G[加湿段]
    G --> H[风机段]
    H --> I[机组总阻力/风机选型]
```

每个功能段输出至少考虑两类数据：

- **空气状态输出**：风量、干球、湿球/RH、焓值、含湿量；
- **工程输出**：阻力、功率、冷量、热量、水量、电量、接口等。

> 第一阶段即使某功能段没有自动算法，也必须允许人工填写输出值，使下游功能段能够继续工作。

## 11. 一键计算与批量选型的定义

现有软件已有“一键配置 / 一键计算 / 批量选型”入口，必须重新明确语义。

### 一键计算
按当前段序，从气流上游向下游依次执行**已经具备算法的功能段**；没有算法的段跳过，但必须检查是否存在必要的人工输出参数。

### 一键配置
根据模板和基本工况自动生成推荐段序、推荐段长及默认参数。第一阶段可仅实现模板套用，不要求 AI/复杂算法。

### 批量选型
用于一个工程中多台相似机组复制/批量计算，不应与单机功能段计算混淆。

## 12. 校核与警告机制

增加统一 `ValidationResult`，不要在各窗体中散落 MessageBox 判断。

至少检查：
- 风量是否 > 0；
- 新风量是否超过送风量；
- 新风比是否合法；
- 截面风速是否超限；
- 总宽/高/长是否超过限制；
- 功能段长度是否足够；
- 功能段是否缺必要输入；
- 上游输出是否缺失；
- 风机余压是否覆盖机内阻力 + 机外余压；
- 冷热水供回水温差是否合法；
- 接口数据是否完整；
- 自动计算结果被人工修改时提示“人工覆盖”。

状态建议：
- `PASS`：正常
- `WARNING`：可继续，但需要确认
- `ERROR`：禁止最终出图/提交

## 13. Codex 修改现有代码时的执行原则

### 第一原则：先读代码，再改代码

Codex 应先定位：
- 主程序入口；
- 工程管理窗体；
- 新建工程窗体；
- 新建机组/模板选择窗体；
- 机组截面窗体；
- 功能段组合窗体；
- 各功能段实体类；
- 数据库/配置文件；
- DWG 输出模块；
- 报告生成模块；
- 现有计算模块。

不要根据截图重新创建一套平行窗体。

### 第二原则：优先重构数据模型，避免只改 UI

如果现有参数直接绑定到大量控件或 DataTable，优先增加中间业务模型/DTO，再逐步迁移。UI 只负责显示和编辑，不应成为参数唯一存储位置。

### 第三原则：兼容已有项目数据

- 不直接删除旧字段；
- 数据库变更必须有 migration/升级逻辑；
- 老项目打开后尽量正常显示；
- 新字段提供默认值；
- 如无法兼容，必须在修改前明确列出影响。

### 第四原则：分阶段提交

建议拆成以下阶段：

1. **P0：代码审计与映射**——输出窗体、类、数据库表、DWG模块对应关系；
2. **P1：统一机组/功能段数据模型**；
3. **P2：改造机组创建与限制条件**；
4. **P3：改造功能段编辑器和输入/输出结构**；
5. **P4：改造组合画布、段序、尺寸链和图块体系**；
6. **P5：统一参数汇总、接口清单、报告/DWG输出**；
7. **P6：逐功能段接入自动选型算法**。

每个阶段完成后必须保证软件可编译、可启动、已有基本流程不被破坏。
