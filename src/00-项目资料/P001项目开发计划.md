# P001 项目开发计划

## 计划目标

按四个独立业务模块逐项完善和验收，通过明确的数据与接口契约集成为 AHU 选型工作流。项目按 L1 人工选型、L2 辅助选型、L3 自动选型逐级建设；没有经确认的规则、数据库或性能算法时，不宣称自动选型或专业性能闭环。

本计划依据当前权威规格 `组合式空调机组选型软件技术规格书_V1.md`、项目维护规则和各模块 README 建立。表中状态是文档基线，不等于本计划已完成验收；每个开发工作块仍需用户批准。

## 模块责任与子 agent 路由

子 agent 以模块角色按任务启动，不假设跨任务常驻。模块内实现由对应角色负责；主 agent 维护总体计划、处理审批边界、协调共享接口并复核集成结果。

| 模块 | 专属子 agent 角色 | 负责范围 | 当前已知边界 |
|---|---|---|---|
| `01-过滤器选型` | 过滤器模块 agent | 排布数据、过滤器选型逻辑、Excel 数据管理和模块测试 | README 记载工作台回传已接入；效率和阻力仍需产品资料确认 |
| `02-盘管选型` | 盘管模块 agent | 标准表查询、截面候选、Excel 数据管理和模块测试 | 可输出参考型号/几何候选；性能需专业软件复核；最终工作台完整接入仍需验收 |
| `03-整机选型工作台` | 工作台模块 agent | 项目/机组模型、功能段链、流程、保存、基础校核与接口适配 | 当前最终页面及 CAS/结果失效规则以维护规则和模块 README 为准；不能据此宣称全专业闭环 |
| `04-3D零件库` | 3D 零件库 agent | 零件数据库、参数化几何、编辑器、稳定 ID、导入导出和模块测试 | 独立库能力已有文档；与最终工作台的完整共享接入仍需验收 |

## 模块目标与开发计划确认流程

每个模块（工作台进一步细分到功能块和功能段类型）按以下流程独立推进：

1. **目标建议**：主 agent 提出该模块建议达到的用户效果、范围、输入输出和验收标准，标明哪些来自现行规格，哪些是待确认建议。
2. **用户修订确认**：用户修改目标或边界；确认后的目标才作为该模块基线。未经确认不进入实现。
3. **现状核对**：对应模块 agent 限定在该模块，按目标检查文档、实现、测试和接口证据，标记已完成、部分完成、未完成和证据不足；不以旧日志代替当前检查。
4. **详细计划与问题清单**：列出逐步任务、涉及文件/接口、依赖、验收方法、问题与风险；区分本模块可独立完成项和需要其他模块配合项。
5. **计划复核**：向用户提交现状、问题清单和详细开发步骤，由用户调整并批准后再实施。
6. **逐块开发与验收**：每次只执行一个已批准工作块，由对应模块角色实现；主 agent 汇报结果、更新本模块维护记录和总体状态。新增范围重新走确认流程。

协作建议：GPT-6.1-Sol 负责需求规划、接口边界和验收方案；GPT-6-Luna 按已批准步骤逐块实现；主 agent 做审阅和集成。模型或子 agent 不可用时明确说明，不宣称完成了该分工。不同模块按依赖逐个推进，不为追求并行而同时改动共享接口。

## 执行与变更规则

1. 阶段表是总体路线图，不授权自动开工。每条用户指令先拆解成可审阅工作块，说明范围、文件、完成条件、验证和依赖，经用户同意后执行。
2. 默认按阶段逐块推进；不同时修改多个模块。接口工作须先获批接口范围，再分别交给相关模块角色实施，由主 agent 汇总和集成。
3. 新发现的需求、文件范围或架构变化不自动并入当前工作块；列为变更项，得到同意后继续。
4. 每个业务模块独立维护 `MAINTENANCE.md`；跨模块完成后更新所有受影响记录及本计划状态。
5. 状态只可在有当前验证证据后标为完成。历史 README 或旧验收记录仅供定位，不替代当前核验。

## 03-0 已确认的维护与保护要求

- 以当前工业工作台 ThreeJS 原型及其直接依赖为唯一维护基准。
- 全项目统一执行清理规则：模块或功能确认完成后，只保留正式入口、实际使用源码、必要资料和维护记录。旧入口、重复页面、废弃脚本和无关资料必须先列出用途、引用关系和影响，经用户确认后移入可恢复归档或从当前项目目录移除；清理后检查正式入口、模块引用和已验收功能。
- 文件职责按模块独立维护：HTML 负责结构和入口，CSS 负责界面样式，JavaScript 按功能负责业务逻辑，`data/` 保存默认数据，`tests/` 保存测试，`tools/` 保存启动/服务/检查脚本，`outputs/` 只保存运行结果和发布文件。模块之间通过明确接口协作，避免跨模块直接改内部实现。
- 整套源码统一管理软件发布版本；模块独立维护变更记录，发布时记录完整文件基线并保留可恢复的旧版。软件版本与客户项目方案版本分别管理。
- 每个模块或独立功能块开发完成后，提交验收结果，由用户明确确认是否允许后续修改；在对应维护记录中登记验收基线、保护文件范围和用户决定。未确认前按受保护状态处理。
- 定期备份：重要修改开始前保留当前稳定 Git 提交；每个工作块完成并验证后上传 GitHub；用户确认模块验收后建立稳定版本标记。上传清单只包含已核对的源码、规则、计划和维护记录，不包含客户项目运行数据、私有零件库数据、缓存或临时文件。
- 用户禁止后续修改的模块，后续变更须先说明原因、影响、文件范围，并取得本次明确授权。用户允许后续修改的模块仍按工作块审批。
- 每次开发列明允许修改的文件与功能范围，交付时核对实际改动是否越界，并验证受影响的已有功能。
- 源码目录整理、启动入口、历史页面处置、文件职责及整理验收的具体方案继续逐项确认；本节不授权迁移源码或改动业务代码。

## 03-1 项目数据与版本管理详细开发计划

**状态：用户审阅中；本节是规划交付，不授权开始修改业务代码。** 本节覆盖工作台子模块 03-1，不代表整个工作台或项目已完成现状核验。

### 目标与已确认规则

- 工作台是项目日常创建、维护、复制和导出的源头；不把下载后的正式 V2 文件重新上传作为当前业务流程。
- 项目和机组在录入/变更过程中保存。打开或查看不改变版本；实际变更完成相关计算并保存后，才更新相应版本。保存失败或导出失败不得伪装成已完成的新下发版本，数据应保留在工作台中供重试。
- 修改已导出的项目时，从上一版延续出新项目版本。复制过程中录入新项目名称，并可修改原项目基本信息；原版本保持不变。
- 新版本中的未修改机组沿用上一版的内容和已有结果；修改机组完成相应计算并保存后，才形成该机组的新版本。新增或删除机组记录在新项目版本中；旧版本仍可追溯。
- 任何一次成功导出都算下发：冻结当时的项目/机组数据作为已下发版本。导出失败可使用工作台中已保存的数据重试，不生成下发记录。
- 导出前不重复执行录入阶段已经完成的专业校核；只做轻量完整性检查，确保将导出的机组、计算结果、图纸、清单和变更记录对应同一版本。字段及专业规则由相应模块在录入/计算过程中校核。
- 成功导出的文件可再次下载，导出文件和项目版本记录至少保留三年。新版本的变更记录比较相邻已下发版本，先分为“参数变化”和“配置变化”；具体字段与版式待确认。
- 项目删除采用可恢复回收站；项目在回收站持续保留，直到用户手动永久删除，永久删除前再次确认。
- 当前原型继续使用本机存储；未来服务器版按三年至少 100,000 条项目/版本记录规划，初期约 20 位技术支持共同使用，并可扩展到几十至上百位销售人员。服务器数据须自动备份到独立存储并验证可恢复。精确服务器、数据库、备份位置和频率后续规划。
- 未来权限由独立权限模块管理：角色批量配置功能权限，并允许对具体人员单独调整。具体角色与功能清单待确认。
- 多人同时修改同一项目的专门冲突交互不列为本阶段需求；项目编号由服务端按销售公司和年月分配，机组序号在同一项目下唯一。项目级导出版本标识仍须满足多人操作下不重复，具体规则待确认。

2. **变更记录细项**：参数/配置各记录哪些字段、展示格式和输出格式；按用户要求后续确认。
